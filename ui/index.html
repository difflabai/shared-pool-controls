01 / The ProblemLocal decisions. Shared consequences.

Everyone follows their own limits.
The pool still runs out.

An agent can have permission to act and still make the shared situation worse. Even well-behaved agents can overbook the same capacity. Our security boundary checks authority and the combined consequences—including commitments that have not finished yet.

01

An agent proposes.

It chooses an approved action and a quantity. The pool’s owner defines the rules; agents cannot rewrite them.

02

The lock checks.

The contract evaluates the resulting shared state, including pending commitments. Hard limits must hold and the configured error score must not increase.

03

Resources are reserved.

An allowed action reserves capacity before dispatch. A denied action can be revised and checked again. Unknown execution outcomes keep their reservations.

V

What is “system energy”? A policy-defined measure of imbalance: unmet work, excess bookings, uneven stock, or stress-loss exposure. The Lyapunov-style check asks whether an agent’s commitment makes that score worse. It does not predict every future event.

03 / Under the contractSmall enough to inspect.

A simple gate.
An explicit boundary.

NEAR holds the shared policy and reservation ledger. Each submission checks the authenticated caller and current state, then reserves capacity in one contract call. Cross-contract dispatch and authenticated callbacks connect that decision to execution.

Why put the gate on NEAR? Independent agents share one contract-owned ledger and a common execution authority. The synthetic executor rejects direct agent calls: changing a browser or skipping a client-side check cannot authorize execution. Real providers would need the same enforced adapter boundary.

Admission ruleConceptual pseudocode
// A proposed commitment
check_authority(caller, recipe);
check_version_and_freshness(request);
next = reserve(state, recipe, quantity);

require(hard_constraints_hold(next));
require(energy(next) <= energy(state));

// Reserve first. Dispatch second.
commit(next);

Recovery from an externally disturbed state has additional checks. See the full specification for exact semantics.

01

A pure Rust core

Bounded data, checked integer arithmetic, fixed recipes. No NEAR dependency in the core’s default build.

02

A NEAR execution boundary

The synthetic adapter accepts execution only from the lock. Callback failure does not automatically release a commitment.

03

A precise claim

Accepted reservations do not increase the configured potential. External events can. Lean model proofs and TLA+ checks are complete; Rust-core verification remains in progress. Explore the formal verification.

Make it yours

Configure it for your own contention problem. Deploy it on NEAR.

Everything that makes the six scenarios different is data. Describe your shared resource in one JSON policy, then deploy the same tested Wasm.

  1. 01

    Name what is scarce.

    Each metric is a quantity the pool tracks, with hard min and max bounds: GPU blocks, MW, inventory, budget.

    Add one metric per window or bucket you need to protect separately. A protected reserve is simply a lower max on the shared bucket.

  2. 02

    Say what “worse” means.

    Each term scores imbalance: Target distance, Excess over a line, or Deficit below one. Admission requires the total never rises.

    Weights decide which problems matter most. Hard bounds and the score are separate checks; a lower score never buys a breach.

  3. 03

    Give each agent a recipe.

    A recipe fixes who may ask (actor), who executes (executor), what is reserved, and what completion changes. Agents choose only a recipe and a quantity.

    requires chains recipes, so a later step can need an earlier one to finish first.

  4. 04

    Build, deploy, initialize.

    Policy is immutable once new runs, so review it first. Deploy and initialize in one transaction from the contract’s own account.

    Then check the code hash, preview as an agent, and submit.

Shape of a policyconfig.json
{
  "name": "api-budget",
  "owner": "you.near",
  "max_age_seconds": 0,
  "metrics": [{ "name": "Requests booked", "unit": "req/min",
                "initial": 0, "min": 0, "max": 100 }],
  "terms":   [{ "metric": 0, "target": 80,
                "weight": 10, "shape": "Excess" }],
  "recipes": [{ "name": "Crawler: batch", "actor": "crawler.near",
                "executor": "api-gateway.near",
                "reserve": [1], "complete": [0],
                "max_units": 40, "requires": [] }]
}
Build and deploy commands +
# 1. Build both Wasm contracts and a provenance manifest
./scripts/build.sh

# 2. Deploy and initialize the lock in one transaction
#    (near-cli-rs syntax; check `near contract deploy --help` for your version)
near contract deploy pool.you.near \
  use-file target/wasm32-unknown-unknown/release/pool_contract.wasm \
  with-init-call new json-args "$(jq -c '{config: .}' config.json)" \
  prepaid-gas '100 Tgas' attached-deposit '0 NEAR' \
  network-config testnet sign-with-keychain send

# 3. Deploy and initialize the executor named in each recipe's "executor"
#    field (api-gateway.near in the example). The bundled pool_executor.wasm
#    is synthetic; use your own adapter for real resources. Without an
#    initialized executor, the first dispatch ends in an "unknown" outcome
#    and the reservation stays held.
near contract deploy api-gateway.near \
  use-file target/wasm32-unknown-unknown/release/pool_executor.wasm \
  with-init-call new json-args '{"lock":"pool.you.near","operator":"you.near"}' \
  prepaid-gas '100 Tgas' attached-deposit '0 NEAR' \
  network-config testnet sign-with-keychain send

# 4. Read the pool back and compare the code hash to your build manifest
near contract call-function as-read-only pool.you.near get_pool \
  json-args {} network-config testnet now

Use the deployment checklist for account setup, then open the NEAR console with your account and expected code hash.

Before you deploy for real +

Replace every executor with an adapter you control. The bundled executor is synthetic: it proves the gate, not a connection to your GPUs, warehouse, or funds. A real adapter must implement the execute and status protocol, idempotency, and authoritative cancellation, and it must leave agents no route around the lock.

Policy and principals cannot be edited after initialization. A pool holds at most 32 metrics, 32 recipes, and 256 lifetime commitments; deploy a fresh pool to rotate. The contract is not independently audited and its formal verification is in progress, so test on testnet first.

What exactly does an agent submit? +

A recipe ID, an exact integer quantity, the state version it reviewed, and a short expiry. Recipes fix the actor, executor, effects, and prerequisites. The agent cannot supply its own risk estimate or ledger delta.

{
  "recipe": 0,
  "units": 2,
  "version": 4,
  "expires_at": "current time + 10 minutes"
}

Illustrative request: the real expiry is an integer timestamp. A stale version is rejected and must be reviewed again.

What happens after approval? +
Reserved→Dispatched→Active→Completed

Unknown execution outcomes keep their encumbrance. Before dispatch, the actor or owner can cancel. After dispatch, release requires definitive nonexecution evidence from the registered executor.

What is—and isn’t—guaranteed? +

The kernel checks the configured bounds and potential against a modeled state. It does not guarantee fairness, profitable trades, truthful external observations, or eventual completion. The immutable policy and registered evidence authorities are part of the trust boundary.

Compute jobs, deliveries, worker payments, and financial positions in this explorer are synthetic. Real-world enforcement requires an adapter without a route around the lock. Dedicated formal verification includes model proofs and checks; Rust-core Kani verification is pending. The verification PR also reports settlement/liveness findings. The contract is not independently audited.
